# WorkBench 部署说明

## 1. 生产构建

```bash
# Windows
wails build -clean

# Linux（Ubuntu 22.04+/Debian 12+，先装桌面编译依赖）
sudo apt-get install -y build-essential pkg-config libgtk-3-dev libwebkit2gtk-4.1-dev
wails build -clean -tags webkit2_41
```

产物均位于 `build/bin/`：Windows 为 `workbench.exe`，Linux 为 `workbench`。

## 2. 桌面分发

- 整个 `build/bin/` 目录打包
- 用户直接运行 `workbench.exe`（Windows）/ `workbench`（Linux）
- Windows 需要 WebView2 运行时（Windows 10+ 自带）；Linux 需要 GTK3 与 webkit2gtk-4.1 运行库（见第 5 章）

## 3. 配置文件

- 首次运行自动创建 `data/` 目录
- 配置文件：`data/directories.json`

## 4. 浏览器访问模式部署

WorkBench 同一二进制内置浏览器访问通道：浏览器打开 HTTP 服务地址即可使用与桌面完全一致的界面（文件、Git、终端、AI 任务全功能）。安全模型：**令牌认证必开 + 默认仅绑定回环地址 + 不内置 TLS**。

### 4.1 两种部署形态

| 形态 | 启动方式 | 行为 |
| --- | --- | --- |
| 桌面同开（默认开启） | 正常运行 `workbench.exe` | 桌面窗口照常，后台同时开启 HTTP 服务；设置「网络访问」开关可关闭 |
| 无头服务（`--serve`） | `workbench.exe --serve` | 跳过桌面窗口，纯 HTTP 服务常驻运行，适合远程访问与开机自启 |

无头模式不依赖 WebView2 窗口，可在无交互会话场景（如远程主机）常驻。

### 4.2 监听地址

| 配置方式 | 说明 | 优先级 |
| --- | --- | --- |
| 命令行 `--listen=<host:port>` | 显式覆盖，如 `workbench.exe --serve --listen=127.0.0.1:36115` | 高 |
| `data/settings.json` 的 `webServe.bindAddress` | 设置页「网络访问」分区或直接编辑配置 | 低 |
| 默认值 | `127.0.0.1:36115`（回环，仅本机可达） | 兜底 |

- **默认绑定回环地址**：仅本机浏览器可达，此时文件预览等免认证路由的信任模型与桌面一致
- 改绑 `0.0.0.0` 等非回环地址须经设置页风险确认（`--listen` 命令行覆盖时不拦截，须自行评估风险）
- 端口被占用：`--serve` 模式启动失败退出；桌面同开模式仅记录警告日志并降级

### 4.3 远程访问建议

服务**不内置 TLS**，跨网络访问须自建加密通道，推荐方案：

| 方案 | 适用场景 | 要点 |
| --- | --- | --- |
| Tailscale | 个人多设备组网（推荐） | WireGuard 加密，无需公网 IP，服务保持绑定回环或 Tailnet IP |
| frp / 内网穿透 | 无组网软件、经公网中转 | 中转链路须启用 TLS（frps 配证书） |
| Nginx / Caddy 反向代理 | 已有 Web 基础设施 | 反代 HTTP 与 WebSocket（`/ws` 路径须支持 Upgrade），启用 HTTPS |

禁止将服务直接暴露公网：明文 HTTP 传输令牌与全部业务数据（含文件内容、终端流、AI 输出）。

### 4.4 访问令牌安全

- 令牌首次启动自动生成，落盘 `data/web_token`（权限 0600），可在设置「网络访问」分区查看 / 复制 / 重新生成（重新生成热轮换，旧令牌立即失效）
- 浏览器端令牌凭据四通道：`Authorization` 请求头 / `X-Auth-Token` 请求头 / `wb_token` 会话 cookie（HttpOnly、SameSite=Strict，30 天）/ WebSocket 子协议（`Sec-WebSocket-Protocol`）。首访以 `?token=<令牌>` 验证后自动建立 cookie 会话，后续请求（含静态资产、RPC、WebSocket）自动携带，无需再次输令牌。除首访验证参数外令牌**不进入 URL**；部署反向代理或访问日志时无须额外脱敏，但仍应避免在代理层打印请求头与 Cookie
- 若链路须经代理，优先使用 WebSocket 子协议或 cookie 会话通道（浏览器端默认行为），避免以 `?token=` 查询参数形式访问——该参数仅为首次手工连通性验证提供，会落入代理访问日志
- 令牌即全权凭据：持有令牌者可通过浏览器访问本机全部文件、终端与 AI agent 能力，请勿外泄

### 4.5 老版本升级说明

老版本配置文件（`data/settings.json`）无 `webServe` 段，升级后**浏览器访问默认开启**（回环 `127.0.0.1:36115`，仅本机可达）。不希望开启时，在设置「网络访问」分区关闭即可，配置持久化生效。

健康检查：`GET /healthz` 免认证返回 `{"status":"ok"}`，可用于探活与连通性验证。

## 5. Linux 部署

### 5.1 产物与依赖

GitHub Release 除 Windows `workbench.exe` 外同时提供 `workbench-linux-amd64.tar.gz`（glibc 基线为 Ubuntu 22.04，兼容 Ubuntu 22.04+/Debian 12+），tar.gz 为扁平布局：`workbench` 二进制 + `README-linux.md` 依赖说明，解压即用：

```bash
tar -xzf workbench-linux-amd64.tar.gz
```

| 运行形态 | 系统依赖 |
| --- | --- |
| 浏览器访问模式（`--serve`） | 无（纯 Go HTTP/WebSocket 服务） |
| 桌面模式 | `libgtk-3-0`、`libwebkit2gtk-4.1-0` 等 GTK/WebKit 运行库 |

Debian/Ubuntu 桌面依赖安装（运行库包，用户机器装这组即可；第 1 章的 `libgtk-3-dev` / `libwebkit2gtk-4.1-dev` 为编译用开发包，仅构建机需要）：

```bash
sudo apt-get install -y libgtk-3-0 libwebkit2gtk-4.1-0
```

### 5.2 serve 模式部署（无头）

```bash
./workbench --serve --listen=127.0.0.1:36115
```

- 首次启动自动在 `data/web_token` 生成访问令牌（权限 0600），浏览器以 `?token=<令牌>` 首访建立 cookie 会话，后续请求自动携带
- 监听地址配置、令牌管理与轮换、远程访问安全建议（Tailscale/frp/反代）同第 4 章，跨平台一致
- 常驻运行可配合进程守护（systemd/supervisor 等按运维习惯配置，应用本体无特殊要求）

### 5.3 桌面运行

```bash
./workbench
```

要求图形会话（X11/Wayland）；WSL2 需 WSLg 支持。内置终端经 PTY 启动 Bash/Zsh/Fish/Sh，文件打开、剪贴板（xclip/wl-copy）、Obsidian（`obsidian://` URI）等系统集成按 Linux 桌面环境自动适配。

自更新：Linux 下载 `workbench-linux-amd64.tar.gz` 后自动解包出二进制，经 `.sh` 脚本完成「等旧进程退出 → 替换 → 重启 → 清理」流程，与 Windows 的 `.bat` 流程等价。
