# Bug 修复工作流

适用于 Bug 定位、问题修复、缺陷消除类任务。

## 核心原则

- 先复现，再修复——不复现不动手
- 最小改动原则：只改导致 bug 的那部分，不顺手重构
- 每个 bug 都要有回归测试
- 不执行 git commit / git push（除非用户明确要求）

## 工作流程

### 第一步：理解问题

1. 明确 Bug 描述：现象、触发条件、预期行为、实际行为
2. 确认环境：哪个版本、哪个模块（Go 后端还是前端）、什么配置（桌面模式还是浏览器访问模式）
3. 如果有错误日志或栈轨迹，完整阅读（后端日志走 `log/slog`，前端错误经 ErrorFormatter 分流）

### 第二步：定位根因

1. 使用 CodeGraph 或代码搜索从报错位置反向追踪调用链
2. 识别可能的原因：逻辑错误、边界条件遗漏、并发问题、配置问题、跨层契约失配
3. 构造最小复现用例

**定位技巧：**
- 先看最新变更记录（git log / blame），排查是否近期改动引入
- 检查异常链，不要只看最外层消息
- 关注边界条件：空值、零值、超大值、并发、异常输入、中文与特殊字符编码
- 跨层 Bug 先核对契约两侧形状是否一致（Go struct JSON 序列化 ↔ 前端消费字段）

### 第三步：编写复现测试

1. Go 侧在对应包的 `_test.go` 编写；前端在对应 `__tests__/*.spec.js` 编写
2. 测试应能稳定复现问题（失败 → 修复后通过）
3. 测试注意本仓稳定性约定：不依赖 mtime 时序、不用固定端口、不用 sleep 等待

**没有复现测试不要开始修复**——否则修了也不知道对不对。

### 第四步：修复

1. 针对根因做最小改动
2. 不要顺手重构附近看起来"写得不好"的代码
3. 保持向后兼容——绑定方法签名、配置 key、错误码不能随意改
4. 如果修复涉及多个模块，从底层依赖开始改

### 第五步：验证

```bash
# 复现测试通过（红→绿）后，跑相关范围完整验证
go test ./...                        # Go 改动
cd frontend && npm run build && npm test   # 前端改动
```

1. 检查是否有其他受影响的测试失败
2. 如果是并发/性能类 bug，考虑多跑几次确认稳定性

## 完成后（agent 只提醒，不代劳）

修复验证通过后**停下**，报告：
- 根因分析
- 修改了哪些文件
- 测试验证结果

提醒用户：
- 如果影响对外行为 → 同步正式文档
- 该类 Bug 若有普遍性，考虑按「规范沉淀规则」沉淀到 `docs/spec/` 或 CLAUDE.md 关键规则

**agent 不做**：不跑完整门禁、不 git add/commit/push。
