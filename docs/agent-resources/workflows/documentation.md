# 文档工作流

适用于正式文档的生成、补全、修订、治理类任务。

## 核心原则

- 文档是产品的一部分，和代码同等重要
- 以代码为准——文档描述的是**实际行为**，不是理想行为
- 不执行 git commit / git push（除非用户明确要求）
- 遵循 `docs/agent-resources/reference/docs-management.md` 文档治理规范

## 文档体系

- **`docs/`** — 正式文档库（全中文，快速入门/功能说明/开发工作流/测试策略/部署说明/开发规范/架构设计/API参考/贡献指南/常见问题/路线图），入口索引在仓根 `CLAUDE.md`「文档索引」表
- **`docs/spec/`** — 跨层契约与深度规范沉淀（索引 `docs/spec/README.md`，两级分流规则见仓根 CLAUDE.md「规范沉淀规则」）
- **`docs/memory/`** — 项目长期记忆（索引 `docs/memory/MEMORY.md`，SessionStart hook 自动加载）
- **`docs/agent-resources/`** — 本目录，agent 内部参考文档
- **`workbench/DEVELOPMENT.md`、`BUILD_SUMMARY.md`** — 开发运维与构建摘要

本工作流主要针对 `docs/` 正式文档。

## 工作流程

### 第一步：明确文档类型

判断需要哪种文档操作：

| 场景 | 操作方式 |
|------|---------|
| 模块有代码能力但缺正式文档 | 生成新文档 |
| 不确定代码改动要不要补文档 | 检查变更影响 |
| 怀疑已有文档与代码不符 | 做一致性审核 |
| 批量检查文档健康度 | 全局扫描 |
| 文档被替代，要废弃 | 归档废弃 |
| 旧文档按当前规范重写 | 迁移重写 |
| 功能完成后 README.md 是否需更新 | 按仓根 CLAUDE.md 首部要求确认 |

### 第二步：确定文档归属

- 面向使用者的功能/安装/FAQ → `docs/` 对应篇目
- 跨层契约、签名同步规则、踩坑机理 → `docs/spec/<topic>.md`（钩子级关键规则再上浮 CLAUDE.md 关键规则行）
- 跨会话项目事实 → `docs/memory/`
- agent 工程规范 → `docs/agent-resources/` 对应目录

### 第三步：编写/修订文档

**文档结构要求：**
- 全中文撰写；层级清晰（`#` 主标题 / `##` 二级 / `###` 三级），优先用 1.1 / 1.2 / 表格
- 重点内容加粗，关键结论前置；数据类内容用表格
- 示例代码完整可执行，命令带生效目录说明
- 禁止空话套话、网络流行语；每段承接上一段，逻辑闭环

### 第四步：与代码核对

文档写完后，必须和实际代码核对：
- 配置项名称、默认值、取值范围
- 绑定方法名、参数、返回值（对齐 `model/` 真实形状）
- 命令示例是否可执行（含前置依赖链）
- 路径、错误码是否真实存在

**以代码为准**，不要凭记忆写。

### 第五步：更新索引

新增或废弃文档后：
1. 更新仓根 `CLAUDE.md`「文档索引」表对应行
2. 更新 `docs/spec/README.md` / `docs/memory/MEMORY.md` 等对应索引
3. 确认链接路径正确、标题一致，无重复或失效链接

## 完成后（agent 只提醒，不代劳）

文档写完后**停下**，报告：
- 新增/修改了哪些文档
- 主要内容概览

提醒用户：
- 提交文档变更
- 如涉及代码变更，和代码一起提交

**agent 不做**：不 git add/commit/push。
